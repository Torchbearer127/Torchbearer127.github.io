借得天光摹镜花，误把虚影作良工

我第一次真正接触 Codex、Claude Code 这一类 AI Agent 工具的时候，最直接的感受其实就是：

太爽了。

那种爽不是“代码补全比以前方便了一点”，而是一种工作方式突然被改变了的感觉、一种好像原始人钻木取到火种的感觉。我本人其实是很不喜欢清洗数据、审阅代码、改 bug 之类的需要大量重复和死扣细节的细碎工作的。以前做一个项目，很多时间其实根本不是花在什么“创造性工作”上：配环境、读文档、处理数据、写 harness、修一些莫名其妙的依赖问题，再加上一堆重复而琐碎的调试。一天忙下来，可能涉及核心问题的时间只有很小一部分，让人觉得好像一天下来一事无成，多少会有些沮丧。

但 Agent 出现以后，这些事情突然都可以交出去。我只需要告诉它我要做什么，它就能自己去读项目、写代码、跑测试、改 bug，甚至顺手帮我把文档也补了。有时候我上午刚冒出来一个想法，中午之前它已经能给我搭出一个能跑的原型。我当时是真的觉得很震撼。脑子里大概就是一句：

“这玩意一上午能干我以前好几天的工作。”

再往后一点，我甚至会想：太好了，以后终于不用把生命浪费在数据清洗、环境配置、胶水代码这种 dirty work 上了，我只负责想最重要的东西就行。

现在回头看，这个判断其实也不能说错。AI 的确非常擅长消灭这些机械性的执行成本。问题是，我很快偷偷把这个结论又往前推了一步：既然这些事情都可以交给 AI，那是不是其他事情也可以？

后来有一段时间，我特别沉迷于用 AI “刮奖”。我觉得“刮奖”这个词还挺准确的。因为有了 Agent 以后，启动一个项目的成本实在太低了。以前突然冒出来一个 idea，我可能还会想一想：值不值得做？要花多久？技术栈熟不熟？这个东西最后到底有没有意义？现在这些问题突然没那么重要了。想到一个东西，我只用动动嘴，先让 Codex 搭一个再说。今天看到一个有意思的 GitHub 项目，我可以让 AI 仿一个；明天想到一个小工具，可以马上让它实现；后天突然对某个新技术感兴趣，又可以临时开一个仓库。

每次开新项目的时候都很兴奋，因为最开始那几个小时，AI 的反馈特别强。文件一下子建起来了，代码刷刷地生成，页面开始能跑，README 也写得像模像样。你甚至不需要理解其中很多细节，就能很快得到一个“已经做了很多事情”的视觉反馈。这件事很容易让人上瘾，所以那时候我启动了很多项目。但尴尬的是，坚持做到最后的好像没有几个。

后来我才慢慢意识到：

Agent 大幅降低了一个项目的启动成本，但它并没有同比例降低把一个东西真正做好的成本。

困难的部分往往还在后面，这个需求到底有没有意义，这个架构是不是合适，这个实现是不是只是表面上能跑，哪些技术债必须现在解决，哪些功能点应该砍掉，什么时候应该重构，什么时候应该停止继续加功能……这些问题并不会因为代码生成得更快就自动消失。但当时的我很容易绕过这些问题，因为开一个新项目，比继续面对旧项目里那些无聊、复杂、需要做判断的问题，有趣太多了。

于是一个 idea 不再像以前那样意味着一种承诺，它更像一张免费的刮刮乐彩票。随手摸一张刮开看看，如果前几下看起来很漂亮，就继续玩一会儿；如果开始麻烦了，那就换下一张。

比“做了很多烂尾项目”更麻烦的是，我逐渐发现，自己好像越来越习惯于不思考。最典型的一件事就是，AI 给出一个方案以后，我越来越少问：“为什么？”而是很自然地点头：“同意，执行。”Codex 说应该这样重构，那就重构；Claude Code 说这个模块最好拆成三层，那就拆；Gemini 给了一套架构，我觉得写的头头是道，看起来挺严谨高级，就直接把它复制丢给 DeepSeek，让它直接去实现。

如果中途出问题了怎么办？也很简单：把报错贴给另一个 AI。甚至有时候，一个 AI 的回复我都懒得自己消化，直接 Command+C，然后 Command+V 给另一个 AI：“它说应该这么改，你怎么看？”另一个 AI 给出一套方案以后，再复制回去。

回想起来，这个过程其实很好笑。几个 AI 在讨论一个项目，而我夹在中间，像一个带键盘的人肉消息队列。最开始我还会觉得这是“多 Agent 协作”、“Human in the loop（人在回路）”之类。后来才意识到，有些时候我根本不是编排精密系统的 orchestrator。

我只是 router，一个自信心被多巴胺填满的 AI 消息路由器。

让我开始觉得不对劲的，是一种很奇怪的陌生感。有些项目明明是我建的：GitHub 仓库是我的，需求是我提的，整个开发过程也是我一直在操作。但有时候重新打开它，我会产生一种感觉：

这东西好像不是我的，它并没有真正进入我的脑子。

我知道这个项目做出来了，却说不清它为什么这样设计。我知道这里有一个模块，却不知道为什么当时选择了这种抽象。我知道某个 bug 被修掉了，但如果让我解释 bug 的根因，可能还要重新让 AI 帮我读一遍代码。如果有人坐在我旁边认真问我：为什么这里用 A 而不是 B？这个组件删掉会怎么样？这里真正的瓶颈是什么？这个设计最大的 trade-off 是什么？很多问题我可能并不能很有把握地回答。这时候我才发现一件事情，一种熟悉而陌生的感觉：

一个 artifact 可以属于我，但构成它的知识不一定属于我。

我确实“做出了”很多东西。但我对这些东西的认知所有权，正在变得越来越弱。

这种状态在“AI 科研”上表现得更加夸张。那时候网上正好很流行各种所谓的“Agent 自动化科研流水线”。网上各类帖子吹的天花乱坠，什么“某某顶会投稿数量爆了”、什么“研究生的末日要来了”之类，说它能够从文献调研开始，自动找 research gap，自动生成 idea，自动设计方法，自动规划实验，最后甚至还能帮你写论文。吃着火锅唱着歌，就能站着把 Paper 挣了。

我甚至一度觉得这就是新时期的科研方式，你学不会好像就会掉队丢饭碗一样。

我当然也去试了，而且试完以后的第一感觉不是怀疑，而是兴奋，因为它看起来实在太完整了。丢进去一个研究方向，它很快就能给你整理出 related work；接着告诉你现有方法有哪些不足；然后顺理成章地提出一个“新的框架”；框架里面模块名字都起得很漂亮；再往后连实验、消融、RQ，甚至论文框架都替你设计好了，再也不用对着天书一样的 LaTeX 编译报错抓耳挠腮了。

那种感觉真的很容易让人产生幻觉。我当时甚至认真想过：照这个效率下去，我是不是一个月就能搞一篇顶会？再夸张一点说，大概有那么一瞬间，我真的会觉得：科研好像也就这么回事，甚至有一点“我就是科研之神”的错觉。现在看当然很好笑，但当时那种感觉其实非常真实。

因为 AI 特别擅长把一件事情的形式补得很完整。它可以给你一个完整的 pipeline：文献调研 → Gap → Idea → 技术路线 → 实验 → 完整论文。每个框里面甚至都有内容。问题是，我后来才慢慢发现：把这些框填满并不难，难的是：

这个 gap 真的是 gap 吗？这个问题值得做吗？为什么之前的人没有这么做？你的创新点是否足够严谨？这个数据集是否足够令人信服？这个 idea 是真正解决了问题，还是只是换了一种复杂的说法？你的实验究竟验证了方法，还是只是在某几个数据集上碰巧取得了更好的数字？我知道这些问题看起来好像有些废话，但是它们都不是把科研 workflow 自动跑一遍就能回答的。但在那个阶段，我把两件事混在了一起：

我把科研产物的形式完成度，误认为了科研认知的真实进展。

现在回过头去看，那其实是我和 AI 相处过程中一个很典型的阶段。最开始，我发现 AI 可以替我承担大量原本繁琐的任务；然后慢慢把思考过程也一起交出去；再后来，连控制权都不知不觉交了出去。而我自己越来越习惯站在最后说一句：“可以，同意执行。”这大概也是最危险的地方。AI 帮我写了多少代码并不是关键，关键在于：

当 AI 开始替我做越来越多事情以后，我自己还剩下什么？

当时的我还没有一个明确的答案。甚至很长一段时间里，我都觉得，只要 AI 足够强，可能这个问题本身就不重要。直到后来，我真的开始让 AI 帮我做科研，并且第一次撞上那些无论烧多少 token、开多少个 Agent，都绕不过去的墙。

我开始怀疑这种工作方式，并不是因为某一天突然意识到“我是不是太依赖 AI 了”；没有那么戏剧化，最开始只是实验结果不好看。那时候我已经很习惯让 AI 帮我做科研了，整个流程越来越自动化，Agent 在后台跑得热火朝天，文件夹里不断出现新的报告、新的实验方案和新的结果表格。

看着这些东西一层一层被搭起来，很容易产生一种奇怪的掌控感：好像研究正在高速向前推进，好像我已经把这个问题吃透了。甚至有时候，实验还没证明什么，一篇论文的故事都好像已经快被讲完了。现在回头看，那其实是一种很虚假的掌控感：

我掌控的更多是一个越来越漂亮的科研流程，而不是那个科研问题本身。

第一次遇到麻烦，是 AI 提出来的 idea 做出来以后，效果并不好。一开始我其实没觉得有什么，科研嘛，实验失败太正常了。而且当时我的第一反应也不是：“是不是这个 idea 本身有问题？”而是：是不是 AI 还不够强？可能模型不够好、推理 effort 开得还不够高、prompt 写得不够完整、上下文给少了，也可能是我现在用的这套科研 workflow 还不够先进。

总之，问题似乎总能被解释成：工具还不够强。

于是解决办法也很自然：换更强的模型、开更高的 effort、塞更多论文进去，把之前的实验结果一起放进 context，让 AI 再仔细想想。如果一个 idea 不行，那就再生成几个；如果几个都不行，那就把搜索空间铺得更大一点。我甚至会在 prompt 里加上一句：“请参考现有论文的 gap 和之前的实验结果，继续提出有潜力的改进方案。”

现在再看这句话，会觉得有一点好笑。因为它看起来很“科研”。有论文，有 gap，有实验反馈，好像已经把一个研究者需要知道的信息全都告诉 AI 了。但实际上，“参考”到底是什么意思？哪些 gap 是真正存在的问题，哪些只是论文作者为了讲故事写出来的 limitation？之前实验为什么失败？失败说明之前的假设错了，还是工程落地有问题？哪些变量已经被排除，哪些现象值得继续追？

这些最关键的判断，我其实一个都没有认真回答。

我只是往 prompt 里面加了一句“参考之前的实验”，然后希望模型自己变聪明一点。

让我第一次产生明显落差的，是后来的一次实验。当时 AI 给我设计了十几种不同的变体和消融方案，从描述上看，每一种都有自己的理由：这里换一个机制，那里增加一个模块，再调整一组参数，或者把之前某篇论文里的设计组合进来。看起来很完整，我也觉得：既然都已经设计出来了，那就跑吧。

当时大概前前后后跑了两三千个 case，花了一百多块钱的 token 和十来个小时的时间。整个过程中 Agent 一直在监控实验进程，日志一直在刷新，新的实验结果不断被写进文件。那种感觉其实很好，你会觉得好像 AI 给你发了一大把奖券，只要运气没差到喝凉水都塞牙缝，多等等总有一张会撞上头奖。然后结果出来了：

没有。

不是“提升没有预想中那么大”，而是押上了这么多时间、金钱和期望以后，这十几种看起来各有道理的方案，甚至没有一个能够稳定超过最朴素的 baseline。

那一刻，我的期待第一次落了空。就好像你揣着富豪托付的神秘信封，信心满满地走进街边高级餐厅，豪气地点上一堆美味佳肴再浇上浓浓的汁。酒足饭饱之后大摇大摆地去结账，拆开信封才傻眼：里面装的竟是一张比我钱包还要干净的白纸。

前每次结果不好，我总觉得再换一个模型、再改一次 prompt、再跑几组实验，事情总会向好的方向发展。但那一次，我已经试了很多轮：模型不算弱，effort 也不低，实验也不少，token 更没少烧。我把自己当时能想到的“AI 不够努力”的理由基本都排了一遍，最后还是没有结果。于是我第一次开始认真怀疑：

会不会问题根本不在 AI 不够强？

后来我才慢慢意识到，当时我的思路其实非常接近一种“科研刮奖”。在最开始的时候，我是在刮项目：想到一个 idea，让 AI 做出来看看；不好玩了，就换一个。到了这里，我开始刮研究 idea：一个方案效果不好，就再生成三个；三个不好，就生成十个；十个还不行，就让 Agent 帮我把组合空间继续展开。潜意识里好像相信一件事情：

只要搜索得足够多，总能撞到一个好的 idea。

而 AI 恰好特别擅长做这种事情。它可以非常快地给出十种、二十种甚至更多“听起来合理”的方案：A 的模块加上 B 的机制，把 C 的评价方式迁移到 D，再加一个反馈环、换一种表示、增加一个 scorer。每一个写成方案 MD 的时候都像模像样，模块名字甚至都可以起得非常漂亮。

但实验失败以后，我开始不得不面对一个以前没有认真想过的问题：

为什么这个 idea 应该有效？

我需要回答的不是“AI 为什么觉得它有效”，而是自己能不能说清楚：这个改动到底针对了哪个真实的失败 case？现有方法为什么在这里失败？我观察到了什么现象，才推导出这个设计？如果这个假设是真的，我应该看到什么结果？如果实验没有出现这些结果，又说明了什么？这时候我才发现，有很多 idea，我其实回答不了这些问题。

它们更像是一些看起来像研究 idea 的组合，而“没有人这样组合过”，和“这个组合有科研价值”，显然不是同一件事情。

后来我对这件事还有了另一层认识。以前我会很简单地觉得：AI 看过那么多论文，当然应该比我更容易想到 idea。但现在看，其实背后藏着一个很大的问题。现在的大模型终究是在大量已经存在的数据上学习出来的。它当然可以把已有知识重新组合，可以做类比、迁移，也完全可能生成训练数据里没有原样出现过的方案。倒不是说“AI 只能复读、不能创新”；而且它确实特别擅长的一件事情：

告诉你在已有知识的分布里，下一步通常应该是什么。

而后来让我觉得困难的是，很多值得做的科研问题恰恰来自另一种提问：为什么大家一直都是这么做的？为什么这个事情几乎所有论文都默认成立？为什么 benchmark 一直这样设计？为什么大家都在优化这个指标，它真的对应我们想解决的问题吗？某个方法每次都在这里失败，为什么没有人认真追这个失败 case？这些问题并不是简单地沿着现有论文继续补全下一步。

有时候反而是在怀疑那个“最理所当然的下一步”。

所以慢慢地，我开始觉得：AI 很擅长扩大搜索空间。但搜索空间大，并不意味着里面一定有价值。更不意味着搜索得越努力，就越接近真正的创新。

广阔的海洋遍布鱼群，并不意味着你捞的够深就能收获；广袤的夜空洒满群星，并不意味着你飞的够远就能抵达。没有洞察力指导的搜索，并不会因为烧掉更多 token，就自动变成Paper。虚妄筑垒起的期望终究会在现实前坍塌为血淋淋的失望。

之前常常以“直觉、聚焦和深入思考”标榜自己的“INFJ”，此刻却好像丢了魂。

而且让我难受的还不只是实验结果，还有组会。那段时间每次要汇报进度，我的流程也已经相当熟练了：把最近的文件和实验结果扔给 AI，“帮我总结一下这周做了什么”；然后“整理成适合组会汇报的结构”；接着“做成 PPT”；最后甚至可以再让它帮我预测老师可能会问什么问题。一套下来非常顺，PPT 也往往做得挺漂亮，研究背景、Motivation、技术路线、实验、下一步计划，一个不少。

但真正站到老师面前的时候，问题开始出现了。有时候讲着讲着，我会突然发现：

好像没有那么清楚自己这一周到底做了什么。

PPT 上写着一条很完整的逻辑链。但是老师如果停下来问一句：“为什么这里要这么设计？”或者：“这个结果到底说明了什么？”我就要在脑子里重新翻找一遍。甚至有些内容，明明是“我的工作”，我却只能模模糊糊记得：这个好像是某次 Agent 分析的时候提出来的。具体为什么……我可能得回去看看。

这其实比实验跑不过 baseline 更让我不舒服。实验失败至少只是说明一个方法没有奏效；但如果我连自己的工作都讲不清楚，那说明问题已经不是实验了。AI 可以帮我生成一份非常完整的进度报告，可以替我总结、画图、做演示文档。但当另一个人坐在我面前，追问一句“为什么”的时候，那些被我跳过去的思考过程，会一下子全部暴露出来。我后来觉得，组会其实像一种很简单粗暴的 review：

这个研究到底有没有真正进入你的脑子。

而那段时间，我经常过不了这个检验。

还有一个现在回想起来有点荒诞的小细节。那时候我也很喜欢让 AI 帮我“整理项目”，结果它会非常认真地给各种实验文件生成 hash、保留旧版本、写验证报告、在中文文档里插入各种抽象的英文名词，再生成一个新的总结。有时候还会在文档里加入各种：“本研究仅限于……”“该结果不代表……”“需要注意的是……”之类非常完整的防御性说明。

每一个动作单独看，其实都挺合理。我说不要覆盖原来的结果，那它就再复制一份；我说要保证文件一致性，那它就算 hash；我说写得严谨一点，它就增加各种限定语。于是，final 变成 final_v2，然后是 final_verified，再然后可能还有一个 final_verified_latest，旁边再放几个 README、hash JSON 之类看似整齐的小玩意。文件越来越多，记录越来越完整，项目看起来越来越“规范”，而我越来越不知道哪个才是最终版本。现在想起来，这件事甚至有一点象征意味：

AI 在努力给我的项目制造秩序，而我自己对这个项目的理解却越来越混乱。

文件的 hash 被校验了一遍又一遍，但我好像从来没有校验过一件更重要的事情：我到底还知不知道自己在做什么？

那段时间我还没有立刻找到答案，也没有突然醒悟，也没有从此决定“再也不用 AI 做科研”。事实上直到现在，我都不觉得答案应该是这个。AI 帮我省掉的大量工作、展开设计空间的能力，以及读代码、整理文献、实现原型系统、做重复实验的效率都是真实的。开始动摇的，是另外一个想法：

我是不是把它能做的事情，和我理应要负责的事情混在了一起？

一开始我只是把执行权交出去，后来思考力也开始交出去；再后来，连“这个方向值不值得继续”“这个结果意味着什么”“这个 idea 到底有没有道理”这样的决定权，也越来越习惯等 AI 先给我一个答案。等到实验真正撞墙，我才第一次发现：有些东西无法靠换更强的模型、把 effort 拉得更高、再烧一百块的 token 补回来。也许我缺的从来都不是一个更强的 Agent，而是我自己还没有对这个问题形成足够清楚的判断。那大概是我第一次停下来，开始重新想：

如果 AI 可以替我做越来越多事情，那么有哪些事情，我反而绝对不能把责任交给它？

衔烛照彻九阴夜，俯首寸步辨伪真

La duda es uno de los nombres de la inteligencia.
“怀疑，是智性诸多名字中的一个。”

——Jorge Luis Borges

实验失败的那段时间，我开始意识到一个有点尴尬的问题：

我一直在要求 AI 给我更多答案，却很少真正回头看看，前面那些答案到底为什么失败。

于是我做了一件现在看起来很普通、但在当时其实算是工作方式转折的事情。我停止继续刮新的 idea 了。不再让 AI 一口气给我生成另外十种架构，也不再想着是不是换一个更强的模型、开一个更高的 effort，就可以把之前没有解决的问题撞过去。我开始往回走。把前几轮那些效果不好的实验重新翻出来。

一开始，我还是让 AI 帮我做了很多事情。它帮我把之前使用过的方法、实验配置、数据、日志和典型 case 重新整理出来。哪些 case baseline 做对了，我们的方法做错了？哪些地方两边都错？哪些结果最反常？对应的输入是什么？当时实际给模型的上下文又是什么？这些东西如果让我自己从一堆零散实验目录里重新翻，可能又要花掉很长时间。所以我还是让 AI 去做。但和以前不同的是，材料整理好以后，我没有马上问：“那下一步应该怎么改？”而是开始自己一个 case 一个 case 地看。

有时候会发现一个很有意思的现象：明明我们的方法理论上给了模型“更多的信息”，结果 baseline 反而做得更好。以前遇到这种事情，我可能会直接让 AI：“分析原因，并给出改进方案。”然后得到 A、B、C、D 四种解释，再顺手设计五个新实验。现在我开始逼着自己先问：为什么？到底是什么信息真的帮助了模型？我们多给的那些东西，是有效信号，还是噪音？是不是缺少了某个真正重要的 witness？是不是工程实现出了问题，本来应该送进去的上下文被意外截断了？是不是 prompt 里的某句话其实已经产生了语义暗示，导致大模型不思考就直接被带偏？同样一个 witness，到底应该直接给源码，还是转成结构化的 JSON？如果 baseline 在这一类 case 上稳定更好，那么它究竟保留了什么，而我们在所谓“增强”的过程中又丢掉了什么？

这些问题没有“给我一个有创新点的 idea”听起来那么激动人心。甚至很多时候，它们都非常琐碎：一个数据格式、一个上下文截断、一段机械的 prompt、几个奇怪的失败 case。但很奇妙的是，那段时间反而是我第一次感觉：

我好像真的开始知道自己在研究什么了。

当然，这个过程并没有脱离 AI。恰恰相反，我还是一直在和 AI 讨论。我会把自己的判断告诉它：“我觉得这里的问题不是模型能力，而是 witness 丢失。”然后让它反驳我。它可能会说还有另外两种解释。那我们就继续去翻日志、看源码、找相关的案例。有时候我会发现 AI 的解释更合理。有时候我会觉得它是在强行把现象讲圆。有时候我们都会错，然后下一组实验又把前面的解释推翻。

我也还是会让 AI 帮我整理文档。每次我都会特别写一个研究笔记，只不过我给自己定了一条很简单的规则：

只有我自己看过、理解过，并且认为证据足够支持的结论，才允许进入那份研究笔记。

AI 可以帮我把文字写得更清楚、统一格式、整理证据，也可以把一大段讨论压缩成几条凝练的观点。但它不能自己决定：“这一条已经可以成为我们的结论了。”这个判断要由我来做。

有时候 AI 会非常自信地说：“因此可以证明……”我会把它改成：“目前的实验说明……”甚至直接说：“这个还不能记，再跑几个 case。”慢慢地，那份笔记对我来说不再只是一个“AI 帮我生成的总结”。它更像是一份我的研究判断的轨迹。里面的句子当然未必是我一个字一个字敲出来的，但每一个留下来的结论，我都知道它为什么在那里，知道对应的证据是什么、它现在有多可信，也知道什么结果出现以后，我应该把哪些内容划掉。

后来我觉得，这可能才是我开始理解“独立思考”是什么意思的时候。以前我潜意识里总觉得，所谓自己思考，就意味着最好不要问 AI。好像一旦和 AI 讨论过，这个 idea 就“不纯”了。但其实科研本来也不是这样的。我们会读别人的论文、问师兄、和老师讨论，也会在组会上被别人指出自己完全没想到的问题。一个观点并不会因为受到了外界启发，就不再属于你。重要的是：

最后是谁在决定自己相信什么。

所以我后来并没有试图把 AI 从科研里赶出去，只是开始把一些东西一点点拿回来：什么现象值得继续追，哪一种解释现在最可信，什么结论证据还不够，下一轮实验到底是为了验证什么，什么时候应该承认这个 idea 不成立。这些抉择重新回到我这里，AI 仍然可以参与我的思考，甚至可以改变我的观点，但“AI 说服了我”和“AI 替我决定了”，是完全不同的两件事情。

也是从那个时候开始，我重新去复现一些相近领域的 SOTA 工作。这一次，我也没有回到以前那种全部手工来的方式。环境还是让 AI 搭，依赖冲突让 AI 修，测试让 AI 跑，几千行日志让 AI 先帮我筛；一篇论文里的实验流程，也可以让它先整理出最值得看的部分。这些事情它本来就比我做得快。我没有任何理由为了证明“我在独立思考”，重新把几个小时耗在装环境上。因为我还是那个不喜欢装环境、改代码这类细碎工作的家伙。我还是很讨厌那些方法论写的天花乱坠、工程实现一塌糊涂的仓库。但 AI 把这些材料准备好以后，后面的事情开始由我接手。

我去看论文声称了什么、代码到底做了什么、它报告成功的 case 为什么成功，也去专门找失败的地方。有时候我会从复现里产生一个猜想，再拿回来和 AI 讨论。如果这个猜想成立，还应该出现什么现象？AI 也教会了我如何设计 micro benchmark 来发现论文 gap。怎么设计一个最小的 micro benchmark，把其他干扰因素尽量拿掉？有没有一个反例可以直接把这个解释推翻？怎么让这个测试用例能够更加一针见血地挖出论文可能的 gap？然后让 AI 帮我把下一轮复现方案搭起来，再跑、看结果，回来讨论。

这个过程中，我慢慢从：“给我一个 gap。”变成了：“这个现象到底意味着什么？”从：“还有什么新方法可以试？”变成了：“如果我的判断是对的，什么证据应该出现？”从：“帮我想一个能超过 baseline 的方案。”变成了：“为什么 baseline 在这个 case 上会赢？”

现在想起来，这可能是一个挺重要的变化。AI 还是很忙，甚至从工作量上说，它可能比以前做得更多，但是方向反了过来。以前是 AI 在驾驶，我坐在旁边不断点：“同意执行。”现在慢慢变成：

我在驾驶，AI 当我的 co-pilot。

我会让它帮我开个雨刮、做个路书或者报个速度，但是方向盘、变速、刹车和油门一个不落的都在我这里攥着。

挺有意思的是，那段时间其实并没有什么特别漂亮的结果：我没有突然搞出一篇论文，也没有一个数字一夜之间暴涨，甚至很多时间都花在复现别人、分析失败实验、做几个看起来特别简单但是一针见血的 micro benchmark 上。如果按照以前那种“这周产出了多少东西”的标准来看，那段时间甚至可能显得不够高效。

但它恰恰是我自己感觉科研思维进步最快的一段时间。

因为以前我可以在很短的时间里得到一个完整的方法。现在我可能花一整天，只为了搞明白：为什么这十几个 case 里有三个特别奇怪。以前我可以让 AI 一晚上给我写出一份像模像样的论文框架。现在那份研究笔记里，一周可能只多出来几条我真正愿意相信的结论。东西变少了。但是这一次，我知道那些东西为什么属于我。

与此同时，我还做了另外一件后来坚持了很久的事情：烛龙。它的起点其实也来自一种类似的不满。

当时我加入了一个开源项目漏洞挖掘和修复相关的项目。之前为了提高效率，我使用过另一套 Agent 漏洞审计系统。第一次看到它的时候，我的感受其实和最早见到自动科研流水线很像。好厉害：完整的多 Agent 架构、精美的 Web 前端、RAG 和结构化的审计规则、各种安全工具，还能自动生成 harness。开始一次审计以后，前端会非常漂亮地展示整个过程：哪个 Agent 启动了、调用了什么工具、现在正在分析什么、又建立了什么任务。整个页面热火朝天，我只需要在精美的网页上点几下。那种感觉真的很容易让人相信：

这么复杂的一套东西，结果一定很靠谱吧。

但用了一段时间以后，问题很快就暴露出来了。首先，它实在太重：每次启动都要用 Docker Compose 拉起好几个容器，前端、后端、各种服务全起来，整个系统才能工作。不过如果最后的效果真的足够好，这些其实也不是不能接受，关键问题是：最后它交给我的东西太薄了。一份报告，里面列了很多“漏洞”、相关代码行、漏洞类型和简单的 description，有时候再附一个两三行的 PoC。看起来成果很多，但开始准备提交的时候，我才发现：其中相当一部分只能叫候选漏洞。有的没有在真实环境中验证过；有的 PoC 根本不足以证明现实影响；有的实际上是误报。最荒谬的是，甚至有些条目的 description 写着写着，自己都会承认这个行为可能并不构成安全问题。

然后接下来怎么办？还是我自己来：重新布置环境，把项目跑起来，一个一个验证，重新确认利用条件，确认影响，写 PoC、保存日志、截图录屏、整理代码证据，最后再把这些东西组织成一份可以提交 CVE、CNVD 或者交给项目维护者看的完整材料。AI 前面做得热火朝天，最花时间的那一段还是留给了我。虽然这套平台确实帮助我取得了一些成果，但效率其实没有想象中高。一个星期下来，能整理并提交出去的漏洞还是没有几个。

于是我开始想一个问题：现在 Claude Code、Codex 这一类 coding agent 本身已经有相当成熟的 Agent runtime 了。Skill、Plugin、MCP 和本地 shell 的相关配套已经很成熟，代码读写、任务规划、工具调用的 Agent loop 一条龙已经被玩的明明白白。这些基础设施别人已经花了大量精力做好了。

那为什么我还要自己重新造轮子，搭一整套 Agent 平台？

我真正缺的，好像从来不是另一个 Web 前端、另一个 RAG，更不是为了“让用户觉得 Agent 在好好工作”画一套复杂的 workflow 图、整一套能够“吸引读者阅读兴趣”的漂亮仪表盘。我缺的是一套适合漏洞审计的工作方法。

于是我开始尝试把自己实际挖洞的流程，一点点沉淀到 Claude Code 这样的现有 Agent 上：不再追求“大而全”，不做一个沉重的平台，也不要求先启动一整套服务。就在本地，就用 CLI，Agent 自己读代码，根据项目情况决定该用什么工具；电脑上有现成的安全工具就直接调用，需要复现就利用 Docker，目标项目本来有 Compose 就尽量复用，缺什么再补什么。

充分发挥主观能动性，就地取材。

我后来把这种思路逐渐做成了烛龙。

但对我来说，烛龙最重要的改变其实还不是“轻量”，而是我开始把自己之前最痛苦的部分，直接写进 workflow 的规则里。比如：什么东西才有资格叫 confirmed（确认）的漏洞？以前一个静态扫描工具的警告可以进报告，LLM 觉得“这里可能存在漏洞”也可以进报告，静态看起来危险也可以先列进去。数字当然会很好看，一次扫描几十条发现，看似满载而归，但最后谁来收尾？还是使用它的人。所以我后来给自己定的原则反而非常保守：

宁可 confirmed 的数量不好看，也不要把没有验证清楚的东西塞给后面的人。

怀疑只是怀疑，候选漏洞就老老实实叫 candidate；静态扫描工具触发的报告只是线索，LLM 的判断也只是线索。能在运行环境里复现，就复现；能给出明确 PoC，就给 PoC；证据不足，就不要装成已经确认。如果最后一个漏洞真的进入 confirmed，那么后面应该跟着的也不再是几句和食堂餐巾纸一样单薄 description，而应该是一套尽量完整的证据链条：漏洞为什么成立、攻击前提是什么、对应源码在哪里、怎样复现、复现日志是什么、PoC 怎么跑、影响是什么。把“嫌疑人”的个人特征、作案动机和作案手法白纸黑字写的清清楚楚。

无论是人还是 AI，无论是要去复核还是要去提交，拿到这些东西以后应该能够继续前面的工作，而不是重新开始调查一次。

就像原著《山海经》中的烛龙：

烛龙口衔火精以照九阴，使无日之极暗之地，亦有光明。其瞑乃晦，其视乃明。

在漏洞审计之中，“视”，是拿到程序运行时确凿的实证，让漏洞暴露在白昼之下，一览无余；“瞑”，是构建出严密完整的证据闭环，在沉沉夜色之中悄然完成取证收网。

一视一瞑，方为一次确凿之审计。

后来我发现，这和我前面重新做科研时发生的变化，其实是一回事。科研里，我开始不再追求：“AI 能不能再给我十个靠谱的 idea？”而是开始追问：“这个结论到底有什么证据？”烛龙里，我也不再追求：“Agent 能不能一次找出五十个漏洞？”而是开始追问：“这五十个里面，到底有几个我真的敢交出去？”它们本质上都是同一个变化：

从追求生成更多答案，变成提高答案进入最终结果之前的门槛。

还有一个变化，是我以前没有做到的。我没有在烛龙能跑起来以后，就立刻去刮下一张彩票，而是留了下来，拿它去审计项目。碰到问题，回来改，再去跑，再遇到新的问题。看到其他 Agent workflow 里有好的设计，就研究它为什么好，再考虑能不能吸收进来。有一次发现输出的证据还是不够方便复核，就继续强化报告契约；遇到重复 candidate，就想办法做去重和状态管理；发现不同 Agent 或不同 session 之间容易丢东西，就继续改持久化和恢复机制；支持新的 Agent 框架，补验证器、补测试，继续做真实项目测试。

以前我特别喜欢项目最开始的几个小时，因为那个阶段 AI 可以让一切看起来进展神速。现在我反而开始习惯让项目待在一个不那么有多巴胺的阶段：维护、重构、修边界条件、改文档，以及处理真实用户或者真实项目里出现的麻烦。这些事情没有“今天又开了一个新项目”那么刺激。但烛龙也确实开始帮我省时间。很多以前需要自己重复做的漏洞挖掘和证据整理工作，被 workflow 自动化掉了，我的审计效率提高了很多。它也确实帮助我拿到了不少漏洞编号，收到了开源社区的致谢和认可。这些结果当然让我很开心。但比这些结果更重要的一件事可能是：

这是很长一段时间以后，我第一次觉得自己真正“拥有”一个 AI 帮我做出来的项目。

不是因为里面每一行代码都是我手写的，实际上当然不是；也不是因为每一个设计最开始都是我独自想出来的，也不是。而是如果现在有人问我：为什么烛龙要这么做？为什么一定要区分 candidate 和 confirmed？为什么我不想再造一个完整的 Agent 平台？为什么证据约束要这么严格？为什么宁可少报也不愿意把未经验证的东西塞进结果？这些问题，我知道答案。因为这些设计不是 AI 从某个“最佳实践”列表里替我挑出来的。它们来自我自己实际踩过的坑、一次次失败、那些让我浪费了时间的误报，以及提交漏洞时不得不重新补齐的证据。然后我再让 AI 帮我把这些经验变成代码、规则、测试和文档。

绕了一圈，我好像终于实现了第一次接触 Agent 时最想要的那件事情：

让 AI 去做那些机器应该擅长的事情，把我的时间留给真正需要判断的地方。

只是当时的我还不明白，“把 dirty work 交给 AI”并不是一句简单的：“AI，你来做。”真正困难的是另一半：

哪些东西我绝对不能因为 AI 做得很快，就顺手一起交出去？

后来我的答案开始变得清楚一点。AI 可以帮我搜索、归纳、写代码、跑实验、搭环境、翻日志、挑战一个新的构想，甚至可以和我一起推演一个新的 idea。但什么证据值得相信、什么结论值得留下、哪个异常值得继续追、什么时候应该推翻自己、最后什么东西可以署上自己的名字交出去，这些事情，我开始重新要求自己负责。

这里的“负责”，并不是说从此以后每一行代码都必须自己写，每一个实验都必须自己跑，也不是要求自己变成一个什么都懂、永远不会判断错的人。而是当一个 AI 生成的东西准备进入我的项目、进入我的研究结论，或者最后署上我的名字被交出去的时候，我希望自己能够说一句：这个东西我看过、我了解、我能够为之负责。

别急，让子弹先飞一会儿。

至少，我得知道 AI 大概在做什么、为什么最后选择了这个方案，也知得道哪些地方我确认过、哪些地方其实还存在不确定性。

如果有一段我没看懂，我不再因为“AI 输出中英混杂太难读”“专业术语太多”“这个 workflow 人工插手以后效率会下降”之类的理由直接跳过去。看不懂，那就问：让它换一种方式解释、指出对应源码，让我看看真正执行的命令，把抽象概念落成具体实例；必要的时候自己去翻原始数据、日志和论文，一直追到我至少能够形成自己的判断，然后再决定：继续、修改、重新验证，或者直接撤回。

以前我很容易把“Agent 自己跑完了整个 workflow”理解成一种效率。后来我才意识到：

如果最后连我自己都不能解释它做了什么，那么所谓的自动化，很可能只是把本来应该由我承担的认知成本藏起来了。

它并没有消失，只是变成了认知债务，而且迟早会在某个地方一起到期：可能是在组会上老师突然问一句“为什么”，可能是在实验结果完全不符合预期的时候，可能是在一个漏洞报告真正准备提交的时候，也可能像我第一次尝试 AI 科研 workflow 那样，等我终于抬起头，才发现整个 workflow 已经堆满了 gate、authority、audit、hash 和越来越复杂的规则，而我自己已经很难说清楚这辆车究竟为什么开到了这里。所以后来我开始给自己加一个很朴素的要求：

AI 可以执行，但我必须 review。

review 也不是扫一眼做个阅读题，看到没有报错就点头，而是我要尽量理解那些会影响最终判断的部分，然后明确做一次选择：我接受这个结果；我暂时接受，但保留这个不确定性；我不同意，需要修改；或者我们之前走错了，撤回来。当然，我还是会判断错，以后也一定还会，但是没关系。责任并不意味着我必须为 AI 输出提供一种“绝对正确”的担保。它更像是在说：

这是我当前能够确认到的边界，这是我做出的判断；如果以后证明这个判断错了，我愿意回来处理它。

我不再把责任推给：“AI 当时就是这么说的。”“Agent 自己生成的，我也不知道。”“这个 pipeline 自动跑出来就是这样。”因为如果最后决定使用它的人是我，那么至少这一步判断，也应该属于我。那段时间我最大的收获，也因此不只是“AI 会犯错”，而是我第一次意识到：

AI 可以非常勤奋、非常系统、非常有条理地把一件事情做偏。

它可以不停工作、生成越来越完整的文档、让实验不断运行、建立越来越严密的流程，甚至让你感觉一切都在高速推进。真正可怕的是，如果方向盘上没有人，你甚至可能在车已经偏离公路以后，还因为仪表盘上的速度越来越快而沾沾自喜。

所以现在，我越来越愿意把 AI 当成一台极其强大的发动机。它可以替我踩下很深的油门、帮我观察路况，甚至不断建议下一条路线。但方向盘、油门和刹车最终不能全部交给它，尤其是刹车。我需要知道什么时候应该停下来问一句：我们现在到底在做什么？这个结论真的是我们验证出来的吗？这个方向还是我们一开始想解决的问题吗？这个东西如果今天就要交出去，我敢不敢在上面写自己的名字？如果答案是否定的，那就停下来，看懂、修正，必要的时候退回去。

我没有把 AI 从驾驶舱里赶出去，它依然坐在旁边，而且可能比以前任何时候都更忙。只是现在，当我们准备驶过一个岔路口的时候，我希望最后握着方向盘、决定往哪里走，并且愿意为这个选择回来负责的人，是我自己。

我只是终于重新坐回了驾驶座。

独舟难越千重浪，和衷共济探水深

重新坐回驾驶座以后，我又发现：

一个人握着方向盘，并不意味着一个人就一定知道路该往哪里走。

甚至在 AI 时代，这个问题可能比以前更加明显。因为现在把一个 idea “做出来”，实在太容易了。以前有一个产品想法，光是实现第一版可能就要考虑技术栈、前后端、数据库、部署，要写很多代码。很多想法甚至还没来得及做出来，就已经死在了实现成本上。现在完全不一样。我可以下午突然想到一个功能，晚上让 Agent 帮我搭出一个原型：页面有了，后端有了，交互也能跑了，README 甚至都写好了。这依然很容易带来一种错觉：既然它这么快就被做出来了，那这个 idea 应该不错吧？

但“能做出来”和“值得做”，从来都不是一回事。

AI 让实现变得越来越便宜，却没有让另一些问题也同步变简单：这个产品到底解决了谁的问题？用户真的会这么用吗？这个功能点是真实需求，还是只是我觉得很酷？一个设计究竟是真的好，还是因为它恰好符合我自己的习惯？如果只有我一个人坐在房间里和 AI 来回讨论，我们完全可能一起构建出一个逻辑极其自洽、实现极其完整，但其实没有多少人真正需要的东西。我越来越意识到：

AI 时代，闭门造车可能比以前更加危险。因为现在，闭门造车真的可以把车造出来。

也差不多是在这个时候，实验室年会上老师讲了一句话，让我印象很深。大意是，在 AI 能力越来越强的时期，博士生也不能只坐在象牙塔里，盯着论文里的问题，而应该更多去看真实的企业和产业到底需要什么。我当时很认同。我当然还是喜欢科研，也依然希望自己能够把学术问题做深，但我不想只学会在一个已经规定好的 benchmark 上，把数字再提高一点。

我也想知道：一个真实的产品为什么有人愿意用？一个工程系统为什么这样设计？需求到底应该怎么判断？一个想法从“我觉得不错”，走到“别人也愿意使用”，中间究竟发生了什么？工业界是如何在项目开发中进行高效团队协作的？我希望自己能够同时训练这些能力。也就是在这样的背景下，我误打误撞的参加了一次暑期 AI-native 开发实践。我们一起做了一个叫 Flovvas 的产品。

这一次，我进入一个陌生项目时，做的第一件事和以前已经不太一样了。

我没有直接跟 AI 说：“帮我实现这个功能。”而是先让它带着我看现有系统。

这个系统的架构是怎么样的？状态存在哪里？为什么这里要多一层 Store？这个 storage abstraction 又解决了什么问题？我不认识某个前端框架里的概念，就继续问。AI 画的 UML 图没看懂，我就让 AI 沿着时序逻辑重新讲；讲得还是太抽象，就让它直接指出对应代码。以前我很容易因为“这个术语太专业了”“先让 Agent 做完再说”跳过去。现在我开始要求自己至少形成一个心智模型：

我得知道自己准备修改的是一个什么样的系统，我不仅要为自己负责，也要为整个项目负责。

当然，我不可能在开始写第一行代码以前把整个项目全部吃透，那又会走回另一种完美主义。但至少，在我要动的那一块，我希望自己知道它为什么在那里，又会影响到谁。AI 依然是我学习这个系统最快的入口，只不过这一次，它不是替我理解，而是在帮助我理解。

也是在这个过程中，我第一次比较认真地做了一次竞品调研。以前做项目的时候，我很少站到这个角度，最多搜索一下：“有没有人做过类似的？”看看功能列表和 GitHub，然后就回去继续写自己的。这次我花了一些时间去使用一款热门的知识管理软件，自己建内容、组织笔记、使用它的 AI 功能，然后把有价值的地方一条条记下来。

慢慢地，我形成了一个当时觉得挺有意思的判断。那个产品里的 Agent，更像是一个已经存在的知识系统上的辅助者。用户先拥有笔记、结构和知识资产，然后 AI 来帮助维护、整理、检索和扩展这些东西。而我当时理解的 Flovvas，如果真的想成为一个 AI-native 产品，Agent 应该更早地进入整个 workflow。它不只是帮用户维护已经形成的知识，而应该尝试成为用户正在思考一个尚未解决的问题时的 co-pilot。后来我给自己想了一个很粗暴的判断问题：

如果把用户已经保存的所有笔记都拿掉，只给 Agent 一个复杂但尚未解决的问题，它还有没有明确的产品价值？

如果没有，那它可能更多是在给一个既有产品增加 AI 能力；如果有，那 AI 才可能真的参与了这个产品最核心的价值创造。这当然不是一个严谨的定义。但它第一次让我觉得，“AI-native”不应该只是：我们也接了一个大模型 API。它应该更深入地回答：

如果没有 AI，这个产品的核心 workflow 还是同一个东西吗？

后来 mentor 看到我的调研以后，说我对“非 native Agent”的判断比较到位。他说：

真正的 AI 产品可能从设计的第一时间，就应该开始考虑 AI 到底处在什么位置；一个存量应用后面再加 AI，很容易最后只是多出来一个辅助功能。

那一刻我其实挺高兴的，倒不只是因为这个观点得到了认可，而是我第一次比较明显地感觉：

自己好像开始不只是考虑“一个功能怎么实现”，而是在尝试理解“AI 为什么要存在于这个产品里”。

可能也就是从那个时候开始，我逐渐长出了一点属于自己的 AI-native 产品思维。

后来，我开始和大家继续讨论 Flovvas 应该怎么改：哪些体验可以从竞品那里借鉴，哪些地方只是看起来功能很多、实际上带给用户的信息负担会很重，AI 到底应该主动到什么程度，什么时候应该帮用户整理、什么时候反而应该少说一点，加入的功能点应该怎样融入整个产品、而不是变成另一个孤立页面。最后，Library 这条线逐渐交到了我手上。这也是我第一次比较完整地在一个多人项目里负责一条持续演进的功能点。

一开始当然还是 AI 帮我写了大量代码，但很快我发现，团队开发和以前自己开一个仓库完全不是一回事。代码能跑，只是第一步。你要考虑现有架构、已有数据和状态怎么管理，考虑账号切换、异步请求、Undo/Redo，也要考虑一个看起来很正常的操作，在另一个生命周期里会不会留下脏状态，然后写测试、开 PR、等 review。

reviewer 再告诉你：这里有一个 race condition，这里的 ownership 可能不对，这里一个 stale response 会让状态丢失。于是再回去看、重新理解、修改、再测、再 review。一个功能并不是被 Agent “一次生成”出来的。它是在不断接触别人的判断、真实的 bug 和已有系统的约束以后，一点点长出来的。

这让我第一次比较具体地理解了：

AI-native 软件工程，不等于让 AI 一口气把软件写完。

它甚至可能意味着，人要比以前更清楚：谁负责什么、谁 review 什么、一个修改为什么可以被 merge，出了问题谁回来负责？因为 AI 写一千行一万行代码很容易，但 PR 上最后写的是你的名字。

更有意思的是，那一个月我们并没有只讨论代码。很多时候聊着聊着，话题就会从：“这个功能到底怎么实现？”变成：“软件工程为什么会发展成现在这样？”mentor 给我们讲《人月神话》，讲软件工程里的“外科手术团队”。我后来对这个比喻印象很深。

一个真正优秀的外科团队，并不是所有人一起围上去，每个人随机切两刀。团队里当然需要很多角色：有人准备工具、有人观察指标、有人提供信息、有人完成辅助工作。

但最终需要有人理解整体结构、把握宏观状态，并且知道：为什么要在这里下这一刀。

AI 出现以后，这个比喻突然显得更有意思了。AI 完全可以成为一个极其强大的助手：它可以写代码、查资料、跑测试、review、生成方案，甚至同时扮演很多以前需要不同工程角色承担的工作。但这并没有让“surgeon”消失。恰恰相反，当越来越多执行工作被自动化以后，一个能够理解整体、做取舍、判断风险并为结果负责的人，价值反而更加清楚。所以后来我越来越觉得：所谓“AI 不会淘汰真正会思考的人”，重点并不是什么“人类永远比 AI 聪明”。而是：

执行越来越廉价以后，理解、判断和责任开始变得更加昂贵。

mentor 还经常讲一个听起来特别朴素的东西：

Less is More.

一开始我其实很容易把它理解成：系统越简单越好。后来发现不是。真正困难的不是“少做”。

而是你要先理解一个复杂系统，才知道什么东西其实可以不做。

那段时间我们也看了一些新的 Agent Harness。其中一个让我印象很深的设计，是它尽量把 Agent 最终拿到的 Context 和各种能力拆得非常透明：Model、Tool、Skill、Plugin、Hook、Memory、Session。不同的信息从哪里注入模型，都尽量能够看见。于是一个原本看起来像黑箱一样复杂的 Agent 系统，可以被重新理解成一组能够组合、替换和比较的部分。加这一段 Context，效果怎么样？去掉呢？换一个 Skill 呢？相对于没加的 baseline context 到底提升了什么？

我当时甚至半开玩笑地把这种思路理解成某种“面向切片”的 Agent 工程。名字未必准确，但那个思想对我影响很大：

复杂系统并不一定要用同样复杂的方式去理解。

有时候好的抽象，就是把复杂度重新拆到一些能够观察、能够修改、能够验证的小块上。这和我前面做科研时的经历其实非常像：有没有 witness，源码还是 JSON，多这一段 context 和少这一段 context 到底有什么区别；把复杂整体切开、比较、验证，再决定哪些东西值得留下。

后来我们还讨论过一个我很喜欢的区分：简单问题和复杂问题。

当然，这并不是什么严格的科学分类，更像是一个实践上的心智模型。所谓“简单问题”，不代表它容易，而是它的大多数重要变量相对可控：目标比较清楚、评价方式比较清楚、反馈也比较稳定。只要方法基本正确，再持续投入时间，就可以不断提高解决它的概率。很多局部的 Agent 工程问题，其实有点像这样。Agent loop 怎么写？Context 该不该加？这个 Tool 有没有帮助？这个 Hook 放在这里还是那里？都可以实验、替换、做消融实验，也可以和 baseline 比。

可是另外一些问题完全不是这样。一个产品究竟该不该做，就是复杂问题；用户会不会留下，是复杂问题；一个交互放到真实生活里到底舒不舒服，也是复杂问题。设计同样如此：它不只是把几个视觉变量调到“正确答案”，还涉及人的习惯、情绪、文化经验、设备、情境，以及各种我们根本没有放进需求文档里的东西。

我很喜欢同学后来举的一个有点搞笑的比喻：在某些游戏里攻略一个角色，通常更接近简单问题，选项是有限的，规则是设计好的，反馈也是确定的。现实里和一个真实的人相处，却明显不是：天气会变、距离会变、人的状态会变，甚至另一个人本身就拥有自己的自由意志。你不可能总结出一套标准且完美 SOP，然后保证完美结局。

产品也一样。并不是再找一个更聪明的 Agent，写一个更长的 prompt，就可以提前把所有不确定性消掉。

有些复杂度就是不会消失。

这让我后来重新理解了软件工程为什么这么强调迭代。以前我可能会觉得，小步快跑只是：早点出版本，效率比较高。后来我越来越觉得，它还有另外一个更重要的价值：

把复杂度尽快搬到现实里去。

与其坐在白纸前面构思一个完美无缺的软件，不如先做一个很小的东西，给人用，看它怎么失败、看用户在哪里卡住、看我们原来觉得特别重要的东西是不是根本没人碰，然后面对一个具体的失败继续思考。

这和我后来重新规划科研、反对“完美主义”的思路又一次重合了。不要一开始就设计一篇完美无缺的论文，也不要先把所有 claim、方法论和数据集之类的都规划好；先跑一个最小实验，先看看现象到底存不存在，失败以后，再面对那个真实失败继续想。

万物皆有裂痕，那是光照进来的地方。

复杂度没有消失。我们只是把它转移到了一个更容易观察、更容易验证、也更容易和别人一起讨论的地方。

AI 带给我的另一个变化，是能力边界突然变得模糊了。以前我大概不会觉得自己应该去认真研究一个产品的 UI、用户体验或者存储架构。但有了 Agent，我进入一个陌生领域的门槛低了很多。一开始这当然让我很兴奋，后来 mentor 又给我们讲了“贡献域”这个概念。他把一个人在团队里的描述拆成了几套独立的语言：你此刻是什么身份，是一回事；这个周期承担什么角色，是另一回事；而你长期在哪个方向创造价值，又是另一回事。我后来觉得，这个区分在 AI-native 团队里尤其重要。

AI 让一个人的能力变宽，并不意味着一个人从此不需要自己的锚点。

我可以借助 AI 写前端，可以研究产品，可以分析竞品，可以讨论设计，也可以继续做研究。但“我能做什么”和“别人为什么愿意长期和我一起做事”，并不是同一个问题。后者要求的是：在某一个方向上，我开始形成自己的判断、品味、经验和责任感，并且能够持续交付别人真正需要的结果。其实到现在我还没有完全想清楚自己的贡献域会在哪里，但是没关系。也许 AI 时代真正值得寻找的，并不是一个越来越窄的职位标签，而是：

当能力边界不断扩张以后，我究竟愿意在哪一块长期承担判断，并把它做成别人可以依赖的东西。

现在回头看，我觉得这可能也是 AI 时代一个很容易被忽略的变化：AI 极大增强了我们处理那些可控变量的能力，以前一个局部问题可能要查一天文档，现在可以让 Agent 几分钟帮你定位；以前实现一个原型要一星期，现在可能一个晚上。但那些本来就依赖真实世界反馈的问题，并没有因为模型更强就自动变成简单问题。甚至恰恰因为前面的执行部分变得太快，我们更容易忘记后面那些困难的部分还在那里。

Implementation is becoming cheap. Reality is not.

所以一个 AI-native 团队真正重要的，可能也不只是大家会不会用 Codex、会不会写 Skill、会不会扒 Agent Harness，而是有没有办法让这些被 AI 加速的实践更快地撞上真实的反馈。然后大家愿不愿意坐下来，一起看、一起争论、一起 review、一起承认刚才的判断可能是错的，然后再继续做。

我觉得很幸运的是，这个八月我刚好遇到了一群愿意做这种事情的人。大家来自不同专业，有和我一样的计算机大类；也有机械、医学和建筑学这种令人难以一下子和 AI-native 联想到一起的专业。有的人对 Agent 架构感兴趣，有人特别关注 UI/UX，有人会分享最新的 Harness，有人把软件工程书里的理论拿出来和现在的 AI coding 对照。看到好的测评帖子就扔进群里，发现一个设计很奇怪，吃饭的时候也能继续聊。

有时候一个问题本来只是：“这个按钮到底放哪？”最后可以一路聊到：“一个产品到底应该替用户做多少决定？”然后又从产品聊到 Agent，从 Agent 聊到人的学习，再从人的学习聊回软件工程。

那一个月我们一起头脑风暴、一起开发、一起 review、一起学 AI，也一起吃饭、一起聊天侃地。每天好像都有很多东西在发生，天气很热，事情很多，食堂的饭菜也很贵，但很充实。后来我才发现，我们几个人居然都开始写博客了。这其实也不是巧合，mentor 当时有一句话，我后来越来越觉得有味道，大意是：

每一件事情都多思考一步，你会得到成倍的回报。

不是说每天都要强行把一件普通的事情拔高成哲学，而是实践结束以后，不要让它就这样过去。

这个 bug 为什么会出现？这次 review 为什么我没想到？这个产品为什么让我觉得舒服？为什么一个看起来功能更多的系统反而更难用？为什么这次团队合作比我一个人效率高？我到底学会了什么？有些东西，做完的时候其实还不属于你。只有当你重新回头，把经验拆开、比较、抽象，再试着用自己的语言解释出来，它才慢慢开始沉淀，进入你的认知。

Créer, c'est vivre deux fois.
“创造，就是活两次。”

——Albert Camus

从这个角度看，写这篇博客本身好像也是这次暑期实践的一部分。我们不只留下了一个代码仓库、一些 PR、几个功能点的实现，以及 Git 历史里的一串 commit，还各自坐下来，试着解释：

这个炎热的八月，我们到底改变了自己什么。

也许这就是所谓的——多思考一步。

归去，也无风雨也无晴

其实你应该也发现了，我写这篇博客的时候也部分使用了 AI 生成，这么大的篇幅也不太像一下子能手敲出来的。

但是没关系。这里面的经历是我亲历的，观点和判断也是我在这些经历、讨论和反思中一点点形成的。AI 做的最多的不过帮我整理格式、丰富内容罢了。在我给出模糊的想法时，AI 会帮我理清楚我的思绪，让我更加清楚自己学了什么、写了什么、想了什么，帮我把脑子里面模糊的风景和遥远的目的地拆解、重组，最后绘成一幅规整清晰的地图。

更重要的是，这一回我清楚我的博客中的一字一句究竟在说什么。

我可以为我的博客内容负责，哪怕里面很多的字都不是我亲手敲出来的。我依然还是那个“固执”的我，不会因为他人说辞而轻易改变信念的我。我当然会因为新的证据、失败的实验和真正有说服力的讨论改变自己的判断，但不会仅仅因为一个声音说得足够漂亮、足够笃定，就轻易把自己的判断交出去。

以前别人做不到。

很显然现在 AI 也不能。

莫听穿林打叶声，何妨吟啸且徐行。
竹杖芒鞋轻胜马，谁怕？一蓑烟雨任平生。

——苏轼

这份心境，便是我对这段“AI 奥德赛岁月”最好的注脚。
